# 04 — Migration Strategy, Dual-Class Fixture Governance & Parity Policy

- **Governing Authorities:** `Patroner_Living_Project_Monograph_v5.16_Consolidated_Master.pdf` (`Ch. 10`, `App. A`, `App. B`), `Addendum v4.1`, `Dossier 03`, `Dossier 06`, `ADR-005`
- **Purpose:** Define the non-mechanical migration policy from the current TypeScript repository (`e9d99cb4`) to the authoritative Python + Next.js architecture, establish governance for **Legacy Reference (Class A)** versus **Normative (Class B)** fixtures, and specify exact parity criteria across all seven engineering domains.

---

## 1. Governing Migration Rule: No Mechanical Translation

The existing TypeScript codebase (`src/engine/*`) was built iteratively across Milestones `03.1` through `05.2.1-R2`. While many of its algorithms are mathematically sound, several modules contain browser-era shortcuts (such as `.toFixed(2)` intermediate point quantization in `math.ts`, 16-step linear Bézier sampling in `contour-validator.ts`, hardcoded bodice-only grading in `pattern-grader.ts`, and the residual defects `DEF-M00-01` through `DEF-M00-06`).

Therefore:
1. **Never translate TypeScript into Python mechanically line-by-line.**
2. **Every Python module must be designed from its governing specification (`v5.16` and Dossiers 01–16)** and verified against independent mathematical oracles (`M00.3`) and normative domain invariants (`M00.5`).
3. **Never preserve a legacy TypeScript bug merely to achieve byte-for-byte output equality.** When an intentional defect fix or precision upgrade alters numerical or geometric output compared to the legacy TypeScript implementation, record the delta explicitly, increment `engineVersion` (e.g., from `0.4.6.1.1` to `2.0.0-py-normative`), and validate against **Class B Normative Fixtures**.

## 2. Dual-Class Fixture Governance (`Task B §5.1` & `ADR-005`)

All test vectors and golden fixtures stored under `contracts/fixtures/` must be partitioned into two strictly separated classes:

### Class A — Legacy Reference Fixtures (`contracts/fixtures/legacy_reference_v0/`)
- **Definition:** Exact, immutable recordings of what the audited TypeScript repository produced at commit `e9d99cb4afc54057850f920dc909b23ebde86f1f` (code `84fffb1f0676dc14e192bf5106c36a469c54a448`).
- **Required Metadata:** `fixtureClass: "legacy-reference"`, `sourceCommitSha: "e9d99cb4afc54057850f920dc909b23ebde86f1f"`, `legacyEngineVersion: "0.4.6.1.1"`, `modulePath`, `inputPayload`, `recordedOutput`, `knownDefectIds: string[]`.
- **Permitted Use:** Differential regression analysis, documenting where and why the new Python engine diverges from legacy TypeScript, and verifying backward-compatible reader/verifier support where historical snapshots are inspected.
- **Prohibited Use:** Class A fixtures must **never** be asserted as the target pass criterion where `knownDefectIds` is non-empty or where intermediate `.toFixed(2)` truncation degraded geometric precision.

### Class B — Normative Fixtures (`contracts/fixtures/normative_v2/`)
- **Definition:** Independently verified expected behaviors derived from analytical mathematical solutions, 80-digit Python `decimal.Decimal` / exact `fractions.Fraction` quadrature oracles, RFC cryptographic standards (NIST FIPS 180-4 SHA-256, RFC 8032 Ed25519, RFC 8785 JCS), and approved garment-engineering rules (`Dossiers 01–16`).
- **Required Metadata:** `fixtureClass: "normative"`, `normativeSchemaVersion: "2.0.0"`, `governingRequirementIds: string[]`, `oracleDerivationMethod`, `inputPayload`, `expectedOutput`, `numericalTolerancePolicy`, `reviewerApprovalStatus`.
- **Permitted Use:** Primary acceptance gate (`AC-02`, `AC-03`, `AC-05`, `AC-06`, `AC-10`, `AC-11`) for all Python modules in `M01`–`M08`.

## 3. Seven-Domain Parity & Equivalence Policy

Parity between legacy TypeScript (`Class A`), independent mathematical oracles, and the target Python engine (`Class B`) is defined separately across seven domains:

| **2. Cryptographic Operations** | **Exact Bit-for-Bit Equality** | SHA-256 digests (`64` hex chars) and deterministic RFC 8032 Ed25519 signatures (`128` hex chars) must match **100% bit-for-bit** against NIST/RFC vectors and valid Class A/B fixtures. | Zero tolerance for divergence. |

| **4. | **7. Authorization & Tenant Boundaries** | **Strict Deny-by-Default Enforcement** | 100% parity on verifier-level tenant/project/garment/scope/expiry/JTI checks, augmented in Python `M01` by server-side Person/Org/Tenant RBAC+ABAC and PostgreSQL RLS. | Server-side enforcement replaces client-side `unauthenticated_local_session` UI toggles for production workflows. |

## 4. Complete Subsystem Migration Disposition Matrix (`Task B §5`)

Each existing subsystem in `src/` is assigned one of seven formal migration dispositions:
- **Retain as Reference (`REF`):** Keep read-only during `M00`–`M05` for differential comparison, then archive.
- **Port after Independent Verification (`PORT-V`):** Port verified mathematical algorithm and invariants into Python after closing any `M00` defects.
- **Reimplement from Governing Specification (`REIMP`):** Build clean-room in Python from `v5.16` and Dossiers because legacy TS is a partial/divergent approximation.
- **Integrate behind New Contract (`INT-C`):** Refactor UI component into Next.js (`patroner-web`) consuming versioned Python DTOs.
- **Redesign (`REDESIGN`):** Replace architectural structure to satisfy multi-tenant persistence, job orchestration, or 3D/financial requirements.
- **Retire (`RETIRE`):** Remove demo stubs and client-side domain execution paths.
- **Defer (`DEFER`):** Hold until prerequisite milestones exit.
